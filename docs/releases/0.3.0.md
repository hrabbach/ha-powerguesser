# PowerGuesser 0.3.0

This release makes **guided capture** an everyday feature: you can teach PowerGuesser a device run
from the dashboard, from the options-flow Capture menu, or from an automation (NFC, voice or a
physical button), and every capture now feeds the next learning run as a labelled example. The
learning engine can also propose a confirmed device's update from its clean captures, through the
existing gate and an explicit Accept.

## What's new

- **Capture from the dashboard.** Four entities and a status sensor drive a capture with no service
  call: `sensor.powerguesser_capture_status` (`idle` / `recording` / `resolving`),
  `button.powerguesser_start_capture`, `button.powerguesser_stop_capture`,
  `select.powerguesser_capture_target` (`new_device` / `candidate` / `device`) and
  `text.powerguesser_capture_label`. The select and label survive a restart.
- **A Capture menu.** *Settings → Devices & services → PowerGuesser → Configure → Capture a device
  run* now offers Start a live capture, Stop the live capture, Capture a past run and Recent
  captures. Every step returns at once; there is never a waiting or progress step.
- **A capture event for automations.** Every capture that reaches a terminal state
  (`done`, `failed`, `cancelled`, `interrupted`) fires one `powerguesser` event with
  `type: capture_finished`, carrying the capture id, state, quality, reason, target kind and id,
  step, duration, energy, a near-twin flag and the earlier-runs count. The event carries **no
  label** (read it with `powerguesser.capture_list`). `docs/CONFIGURATION.md` carries ready-made
  **NFC, voice and physical-button recipes**, a `capture_finished` notification recipe, and the
  full event-data table.
- **Similarity and earlier runs.** A settled capture now shows the most similar candidates and
  confirmed devices (with a **near twin** flag when one is the same load), and how many runs
  already in the buffer the captured signature would have matched, with the days its basis covers.
  It is **advisory only** and never blocks Confirm.
- **Captures teach the next learning run.** Every capture that snaps to a run becomes one numeric
  example (step, duration, energy, coarse hour and weekday, cluster) in the next learning run,
  with no timestamps and no capture id. The preview action's body is byte-identical to the body the
  run sends. The model may return an optional per-example verdict, shown as `llm_verdict`.
- **Device update proposals from captures.** Clean captures aimed at a confirmed device are batched
  into the next run; a `capture_refit` stage refits the device and the existing no-regression gate
  decides, judged on validation days that exclude every captured window. Accept the update from the
  device menu (a new version that rollback can undo); nothing changes in place.

## Consent

Your existing LLM consent now also covers **capture examples**: each capture you settle adds one
numeric example per captured run to the next learning run's request (step, duration, energy, hour,
weekday and cluster — never a raw history and never a timestamp). The capture's **label** is sent
only if you have opted in to share entity names; without it, examples carry opaque ids. No new
consent class is needed and the consent schema is unchanged — the request still goes to the same
endpoint you already approved, and the on-screen consent notice and the `share_entity_names`
description now say so.

## Install

Upgrade over 0.2.3 through the Home Assistant Marketplace ("Add from link",
`https://github.com/hrabbach/ha-powerguesser`), then restart Home Assistant. The upgrade needs no
reconfiguration and touches no stored device data. This build installs over 0.2.0, 0.2.1, 0.2.2 and
0.2.3.

## Known limitations

Unchanged from 0.2.3: this is a **0.x release** (the hardware UAT is still open); **30 s meters are
the design baseline**; step detection needs an **effective interval of 45 s or less**; **program
devices cannot be merged** in v0.x; and some device classes legitimately read **not validated**.

Specific to this release:

- The **near-twin threshold and the earlier-runs timing are initial values** — they are not yet
  measured on a Raspberry Pi or against a real buffer, so similarity ranking and the earlier-runs
  count are best-effort until they are calibrated post-ship.
- **Many capture-driven device refits end without a proposal.** A few extra runs rarely move the
  learned boxes (they are fitted from percentiles widened by 5 %), so the value is mostly better
  coverage for a run the active version missed rather than a new proposal.
- A single capture is still **not an accuracy claim**; it seeds a preview that needs the normal
  Confirm and learning steps, and (for a device) an explicit Accept.
- A captured run is judged from the whole-house signal; a run that overlaps another load can be
  refused as **contaminated** rather than captured, and contaminated or ambiguous captures never
  train a device proposal.

## Accuracy

No new accuracy figure is claimed here. Accuracy remains the README table, generated from the
validation report; classes without a passing validation read "not validated".
